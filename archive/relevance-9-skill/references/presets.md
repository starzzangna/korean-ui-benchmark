# 목적별 시작 판단

카테고리가 고정 색과 레이아웃을 결정하지 않는다. 사용자·자료·과업을 먼저 보고 [visual-direction.md](visual-direction.md)와 [scene-motion.md](scene-motion.md)를 연결한다.

| 목적 | VARIANCE / DENSITY 시작값 | 장면 | 조작 |
|---|---|---|---|
| 브랜드·소개 | 5 / 4 | 주인공의 성격에 맞는 calm/flow 검토 | 대표 행동과 사진/프레임의 감속 연결; 업무는 짧게 |
| 포트폴리오 | 7 / 3 | 작업 감상과 진입에 calm 검토 | 필터 즉시, 상세/확대의 명확한 피드백 |
| 행사 | 6 / 4 | 타이포/포스터 장면에 calm 검토 | 시간표·합계 즉시, 확인 맥락은 짧게 |
| SaaS 업무 | 3 / 7 | 기본 none | 검색·필터·상태 즉시, 결과/상세만 선택적으로 |
| 커머스 탐색 | 4 / 6 | 브랜드 소개 장면에 한정해 판단 | 옵션·가격·재고·주문 상태 즉시 |

수치는 조정 가능한 시작값이며 품질·국내 사용자 통계가 아니다. 같은 페이지 안에서 소개와 데이터/폼의 리듬이 달라도 된다. 밀도를 작은 글자·작은 조작 영역으로 해결하지 않는다.

## SaaS

상태·검색·목록·다음 행동이 먼저다. 요약 수치와 막대는 같은 데이터에서 계산한다. [visual-review.md](visual-review.md)로 정보 계층을 본다. 빈 결과는 초기화, 실제 요청 실패는 입력을 보존한 재시도를 제공한다. 모바일은 중요 열과 상세 경로를 유지하며 표 가로 스크롤이 문서 전체로 번지지 않게 한다.

## 자료와 연동

## 업무 진행 요약과 다가오는 업무

진행 요약·다가오는 업무를 기본 구성으로 추가하지 않는다. 상태 현황과 검색·업무 목록만으로 사용자의 과업이 해결되면 거기서 끝낸다. 보조 영역 때문에 목록 폭이 줄거나 첫 업무가 아래로 밀리고 이미 있는 수치·업무가 반복되면 먼저 생략한다. 감성 문구를 넣기 위한 요약 카드를 만들지 않는다.

별도의 모니터링·마감 확인 과업이 명확할 때만 작은 진행 요약 또는 마감 목록을 선택한다. 두 영역을 세트로 넣을 필요는 없다. 사용한다면 실제 완료 수/전체 수로 진행률을 계산하고 완료 제외·마감일순의 다음 업무를 제한해서 표시한다. 목록 필터와 별개의 전체 기준이면 이를 문구로 밝힌다. 보조 정보를 뺀 화면과 비교해 핵심 목록의 가독성·탐색이 나아지는지 판단한다.

상태 저장·업무 추가 후 같은 데이터로 요약을 다시 계산한다. 제목·담당자·기한을 함께 보여주고 선택 시 기존 상세로 연결한다. 전체0개와 전부 완료를 구분하며 빈 목록에 가짜 업무를 채우지 않는다. 실제 작업 흐름이 있는 앱에 감성 문구를 의무로 넣지는 않는다.

정적 HTML은 [task-summary.js](../assets/patterns/task-summary.js)와 [task-summary.css](../assets/patterns/task-summary.css)를 선택적으로 쓸 수 있다. `KoreanTaskSummary.render(container, tasks, {onOpen})`에서 각 항목의 `id/title/owner/due/status`를 사용하며 `onOpen(id, button)`은 기존 상세 열기 함수에 연결한다. 기존 프레임워크에서는 같은 계산·빈 상태·초점 계약을 현재 컴포넌트로 구현한다. 이 패턴을 쓰기 위해 스택을 바꾸지 않는다.

포트폴리오는 역할·작업·과정을 구분하고 실제 성과를 지어내지 않는다. 커머스는 옵션에 가격·상태가 실제 따라가게 한다. 소개 페이지의 후기·로고·긴급성은 확인된 자료가 있을 때만 쓴다. 실제 연결 없는 신청·구매·문의는 데모이며 운영 서버의 완료처럼 보고하지 않는다.
